# 候选评分固定参数与初始种子优化

日期：2026-09-21。接续 [剪枝上下文复用](scoring-prune-context.md)，继续处理组队候选评分成本；不修改控分搜索。

完成本轮优化后，与迁移前旧整数版的关闭诊断直接复测见 [当前浮点引擎与旧整数引擎对照](scoring-integer-current-comparison.md)。

## 先排除没有收益的缓存

尝试按“完整的第一段整数键分序列 + 技能参数”缓存中间结果。该键严格区分每个 Combo 分段，未使用浮点近似或把相近综合力直接合并；限制在所有技能顺序都可达的摆放组内。实验结果如下：

- 完整技能最优顺序缓存：新档案平均 PT 查询约 2027 万次，命中 219,063 次，约 **1.08%**。
- 改为单卡六个技能位置的分数增量缓存：单行命中约 **26.75%**，整张五人矩阵全部命中仅 **5.21%**。本次原型在部分行缺失时仍重算完整矩阵。
- 分行版本同一审计二进制开启 / 关闭对照，候选构建 **36.986 / 28.560 秒**，总耗时 **54.947 / 49.047 秒**。仅一轮，且其他阶段有波动；不把这一对照当作稳定加速比例。

上述输出和所有非计时 metrics 均与本轮之前一致，但新增查找、键构造和内存开销未能换来收益。两版实验缓存均已撤回，生产代码不包含这些表、键接口或新增审计项。只能据此排除本次实现，不能推导所有粒度、容量的缓存都无效。

## 保留的改动

1. 谱面初始化时给连续倍率段保存精确的 `f32 Combo` 倍率。压缩矩阵和摆放等价检查直接读取，避免逐队、逐曲重算相同的 Combo 规则。合并分段同时要求原始 factor 和 Combo 位模式相等。
2. 压缩评分先计算本曲的基础分与判定倍率乘积，再按每段 Combo 做乘法和第一段取整；普通技能倍率按窗口计算一次。原来的 f32 运算顺序、两段取整和逐键渐强序列不变。
3. 初始三队种子搜索改用已经在正式候选中使用的压缩计分 scratch。压缩内核不适用时仍执行原来的回退路径；队伍搜索、可达顺序和评分规则不变。
4. 没开启诊断时，跳过候选评分和筛选内的逐次计时。开启诊断时保留原有细分数据，所有候选计数和剪枝逻辑不变。
5. 平均 PT 的 `seedMs` 补上最初寻找可行三队及其平均分准备，日志另列 `PT medley initial seed`；后续种子改进照常累加。此字段与之前的 0.18 秒等数字口径不同。

核心改动位于 `model/chart/compressed.rs`、`model/chart/native.rs`、`model/chart.rs`、`medley/seed.rs`、`medley/enumeration.rs`、`pt_maximize/medley.rs`。

## 验证与基准

正确性检查已完成：

- 核心 249、数据层 28、三队求解器 23、WASM 接口 10，共 **310 项 Release 测试通过**，11 项原有忽略项。
- 新增 Combo 预计算与原始每键计算、摆放等价检查对照，覆盖 Combo 阈值、浮点邻接值和单曲/巡回标志。
- 两份完整档案各覆盖 306 EX / 186 HD 单曲最高分与最大平均 PT、协力 PT，共 10 份业务输出与本轮之前一致。
- 实际 WASM 重建，10 组原生/WASM 输出一致，覆盖单曲、巡回、指定队伍、Auto、技能延后、协力及非空控分接口。
- 网页资源标识更新为 `native-f32-6`；计分规则标识保持 `cn-9.4.4-f32-v1`，未更新发行版本、提交或推送。

比较对象为本轮之前已经优化剪枝准备的浮点引擎，未与旧整数引擎混比。以下原生 Release 各一轮，固定同一逻辑核（掩码 4）及进程优先级，开启相同诊断，前后顺序按场景轮换；计时期间没有并行构建或测试。

新档案仍是活动 323 的 186 SP / 395 SP / 772 EX；旧档案是此前诊断的 306 EX × 3。最高分强制精准搜索。四组的业务输出和全部非计时 metrics 逐字段相同。

最高分初始种子从新档案 **4.652 → 1.726 秒**、旧档案 **3.462 → 1.357 秒**，是本轮最清楚的收益。候选评分 `build_candidate_ms` 新档案最高分从 **15.973 → 14.676 秒**；旧档案最高分从 **10.165 → 9.920 秒**，候选构建总时间基本持平。

新档案平均 PT 首轮存在明显波动：未修改的三队求解阶段也从 15.859 变为 11.006 秒，剪枝准备从 4.583 变为 3.896 秒，不能把总耗时的 25.63% 全部归因于本轮改动。其余三组总耗时下降约 8%–12%；同样只有一轮，不作为稳定比例承诺，也不跨轮拼接先前报告中的最快耗时。

补齐计时后，平均 PT 初始种子及其平均分准备分别为新档案 **1.859 秒**、旧档案 **1.139 秒**；包含后续种子改进的 `seedMs` 为 **2.070 / 1.422 秒**。原版本的 `seedMs` 没有覆盖初始种子，不能直接用两版该字段相除。

另外关闭两项诊断环境变量，在同一核心串行补测新档案平均 PT：总耗时 **46.639 → 39.615 秒（减少 15.06%）**，候选构建 **27.653 → 24.593 秒**，CPU 时间 **46.547 → 39.438 秒**。前后业务输出及全部非计时 metrics 一致，且与开启诊断的结果一致。这一对照包含全部本轮改动，不能单独归因于跳过逐候选计时；未测浏览器性能。

本地实验输入、二进制、审计和前后结果存放于忽略目录 `tmp/native-candidate-plateau/`。`audit.exe` 是撤回的完整顺序缓存，`row-audit.exe` 是撤回的分行缓存；`before.exe` / `final.exe` 才是最终对照使用的生产算法。玩家档案不进入版本管理。

最终复现入口为 `compare.py` 和 `compare-no-trace.py`，分别输出 `benchmark-operands-r1.json` 和 `benchmark-no-trace-r1.json`；每轮记录输入/二进制哈希、墙钟、进程 CPU 时间、CPU 周期、峰值内存及完整结果。阶段汇总在 `benchmark-operands-summary.json`。单曲完整档案及原生/WASM 对照用于正确性检查，其执行时可能存在构建负载，不作为单曲或浏览器性能基准。
