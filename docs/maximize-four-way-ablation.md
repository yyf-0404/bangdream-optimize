# 最高得分四项优化拆分对照（2026-09-16）

把上一轮的两个组合拆成四个独立开关，验证单项收益以及在其他三项已经开启时的额外收益。这里只测最高得分；平均 PT 的默认路径未改变。

## 四项分别做什么

| 代号 | 优化 | 单独开启时的实际工作 |
|---|---|---|
| A | 兼容队伍上界 | 对候选 X，分别查询不与 X 冲突的另外两曲分数上界，相加判断 X 是否可能达到门槛 |
| B | 另外两队合计上界 | 限制另外两队彼此不冲突时的最高合计分，暂时不限制它们与 X 的关系 |
| C | 第二队批量过滤 | 固定第一队，使用 AVX2 一次检查四个第二队，按原顺序保存可兼容的位置 |
| D | 第三队前缀复用 | 固定第一队，预先排除与它冲突的第三队；遍历多个第二队时复用这段列表 |

A、B 共享兼容查询这个前置步骤。B 单开时仍需查询各候选的兼容上界，才能得到两队合计上界；A 关闭不代表这些必需查询也能关闭。A、B 都开启时，对每首歌取两个安全上界的较小值。各候选只需在一首歌上通过，因此两项单独保留集合的交集，也不一定等于同时开启后的集合。

C、D 使用编译期布尔专门化。关闭 C 时按原排序逐条检查第二队；关闭 D 时第三队扫描使用第一、二队合并掩码，直接检查原第三队列表。不会计算已经关闭的筛选列表后再丢弃。

## 测试口径

- 新档案：1456 卡，国服活动 323，186 SP / 395 SP / 772 EX。
- 旧档案：1414 卡历史 fixture，自定义活动 0，306 EX 三曲。
- 原生 Rust Release、单进程顺序执行、`StrictExact`，不自动切随机桶，不是 WASM 计时。
- 所有组合使用同一个可执行文件。其他已接入的候选压缩评分、种子缓存、固定规模分配、覆盖剪枝保持开启。
- 每种组合核对完整业务结果与每批原始候选指纹；计时与求解器后端标识不属于业务等价字段。
- 计时不与编译或测试并行。输入、二进制和源码指纹保存在本地实验目录，不提交用户档案。
- 十种开关组合每份档案各两轮，第二轮逆序执行；原扫描器控制组每份档案各一轮。共 42 次完整运行，没有单独预热，也不丢弃较慢轮次。

第一轮顺序为全开 → 全关 → A → B → C → D → 关闭 A → 关闭 B → 关闭 C → 关闭 D，之后跑原扫描器。第二轮将十种组合及每组内的新旧档案顺序反转。未修改的原始候选构建阶段也出现明显波动，因此小幅计时差异只视作趋势，不作为稳定提速结论。

四项全关的公共扫描器仍保留共享实现的分数截止点维护等工作，因此不是逐字节复原旧 AVX2 实现。另测“原扫描器”作为独立控制组；单项表使用同一个公共扫描器互相比，避免将扫描框架差异算进某一项。

“总耗时”是进程启动到结果文件写完的墙钟时间；“扫描”是各次最终候选过滤之后对应的求解器内部计时之和，包括求解器自身的准备，不包括调用前的掩码转换、种子搜索和候选构建。每个候选池与扫描日志逐一对应，空池也计入。阶段不构成完整总账，不能直接相加替代墙钟时间。

## 如何解读

1. **B 是新档案最明确的收益来源。** 单开就将累计候选从 660,565 降到 71,922，最大池从 133,007 降到 26,183。最佳池涉及卡牌从 142 张降至 34 张，掩码从三个 `u64` 缩成一个。全开基础上关闭 B，扫描从 11.400 秒升到 27.716 秒，两轮方向一致。
2. **A 会删候选，但不一定命中热点。** 新档案单开 A 删掉约 45.5% 的候选，最大池却仅从 133,007 降到 132,968。公共扫描器累计逻辑检查从 20,402,024,180 降到 20,295,846,686，只少约 0.52%。在 B 上再加 A 仅多删 117 个候选，未测出稳定的额外提速；旧档案额外删 4,721 个，但不足以单凭两轮波动断言速度收益。
3. **C 单开有效，但组合中的追加收益很小。** 相对公共扫描器全关，单开 C 的扫描均值下降；全开基础上关闭 C 后，新旧档案扫描均值仅增加约 4% / 2%，小于当前运行波动。不能据此声称 C 在剪枝后仍有确定的整轮收益，也不能因此断定 C 应当删除。
4. **D 对剪枝后的新档案仍有效。** 关闭 D 的扫描两次为 16.287 / 16.258 秒，全开为 12.566 / 10.235 秒，均值减少约 29.9%。旧档案的整轮耗时均值几乎不变，不能推广成对所有档案的固定收益。
5. **真实旧扫描器的对照不能省略。** 新档案原扫描器 140.136 秒、全开均值 33.938 秒，收益明显；旧档案 18.922 秒与 18.558 秒基本持平。原扫描器只各测一次，此处用于识别框架差异，不给小幅变化下统计结论。旧档案公共扫描器全关反而比原扫描器慢，因此不能把单项相对公共基线的全部收益归为相对旧版的提速。

A/B 上界自身累计开销均值：新档案 A 0.406 秒、B 0.355 秒、A+B 0.476 秒；旧档案分别 0.223 / 0.220 / 0.249 秒，均已计入总耗时。开关不改变原始候选枚举：新档案仍累计 5,249,105 条、旧档案 3,556,703 条。

以上逻辑检查数只在公共扫描器之间比较，不能与原扫描器的 AVX2 批次计数混用，也不等于实际执行的机器指令数。当前数据中 B 和新档案中的 D 收益最明确。最终接入策略维持四项默认全开，独立实验开关用于后续对照；没有根据这两份档案硬编码选择算法，也不将全开解释为所有档案上的最快配置。

## 正确性与适用范围

- 新档案最高分固定为 10,781,643；旧档案固定为 11,815,764。
- solver 23 项测试通过，2 项原有性能测试忽略。576 组输入逐一核对四种 C/D 组合与原扫描、标量扫描的最优分数及同分队伍索引，覆盖空池、同分、尾部不足四条和不同掩码宽度。
- 共用上界 6 项测试通过；新增测试分别核对 A、B、A+B 在不同索引预算下均保留所有能达到门槛的合法三队。
- WASM core 检查通过，仅有原有未使用代码警告。本轮没有测浏览器 WASM 性能。
- C/D 的专门化覆盖 1–4 个 `u64`；更宽掩码保留原扫描路径。A/B 的受限索引使用保守尾部上界，不会把尚未查询的部分当作无解。
- 实验开关不参与普通生产构建，默认仍四项开启。没有按这两份档案的编号硬编码选择算法。

## 复现

通过 core 的 `experimental-maximize-optimizations` feature 启用同一二进制的实验开关：

```text
BANGDREAM_OPTIMIZE_MAXIMIZE_TEAM_BOUND=on/off
BANGDREAM_OPTIMIZE_MAXIMIZE_PAIR_BOUND=on/off
BANGDREAM_OPTIMIZE_MAXIMIZE_SECOND_BATCH=on/off
BANGDREAM_OPTIMIZE_MAXIMIZE_THIRD_REUSE=on/off
```

既有的 `MAXIMIZE_COMPATIBLE_PRUNE`、`MAXIMIZE_REUSE` 总开关仍保留。前者为 off 时 A/B 不运行；后者为 off 时回到原最大分扫描，C/D 不运行。它们的完整环境变量名前缀均为 `BANGDREAM_OPTIMIZE_`。

本地完整结果、日志与元数据位于 `tmp/maximize-parts-study/`；复用 `tmp/maximize-shared-study/harness/` 的冻结输入加载与计算入口。运行脚本跳过已经完整结束的同名轮次，新增轮次使用 `--repeat=N`。

```powershell
cargo build --release --offline -j 1 --manifest-path tmp/maximize-shared-study/harness/Cargo.toml --target-dir target
python -X utf8 tmp/maximize-parts-study/run.py
python -X utf8 tmp/maximize-parts-study/run.py --repeat=2 noD noC noB noA D C B A none all
python -X utf8 tmp/maximize-parts-study/analyze.py
```
