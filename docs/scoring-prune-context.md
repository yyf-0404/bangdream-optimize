# 组队剪枝上下文复用优化

日期：2026-09-21。接续 [缓存审计](scoring-cache-audit.md)，本轮不再优化控分，集中减少单曲及巡回组队中的重复扫描和复制。

后续候选评分优化和种子计时补齐见 [固定参数与初始种子优化](scoring-candidate-operands.md)。下文保留本轮当时的计时口径。

## 改动与等价性

### 固定卡牌的队友上界

原先按“组队条件、排除的角色”缓存其余四人的综合力和技能上界。第一次遇到每个角色时，重新扫描全部卡牌；命中缓存时仍复制两份动态数组。

现在在每一种组队条件下，先按角色分别汇总最高综合力及每首歌的最高技能贡献，再各保留最高的五个角色。查询时排除当前角色，取剩余前四名作为队友上界、前一名作为额外队长技能上界。查询只返回三个标量，不分配数组。

这里只排除一个角色，因此前五名足以恢复原来的前四名。综合力和技能的排名继续独立计算，不强制它们来自同一张卡；这保持原先乐观上界的定义。求和顺序仍为降序，缺少四人时仍补零。新增回归用浮点位模式对照旧的完整扫描，包含重复角色、多种属性和乐队、空池、不足五角色、并列值及稀疏角色 ID。

源码：`crates/core/src/team_prune/hard/teammate.rs`，由 `hard.rs` 的 `MedleyPruneUpperBounds` 调用。

### 贡献比较共享只读上下界

`signature_context_bounds` 原先虽已缓存计算结果，但每次两卡比较仍深拷贝五组 `Vec<f64>`。现在缓存并返回 `Arc<SignatureContributionContextBounds>`，复用不可变数组。

缓存范围仍限定在同一份卡牌、谱面和道具上下文内；设置新的固定队友后仍清空上下界及延后模型缓存。补强原有队友综合力测试，检查已经取得的旧上下文保持不变，新查询使用更新后的上下界。

### 技能延后存在性只判断一次

原先每次查询延后贡献模型都遍历全部卡牌的 profile 来确认是否存在延后窗口。现于 `MedleyContributionDominance` 构造时保存该布尔值。profile 在上下文存续期间不可变，因此这个值不需要逐对卡牌重算；具体延后状态模型和窗口边界没有更改。

后两项共用 `crates/core/src/team_prune/contribution.rs`，适用于调用此贡献比较的单曲及巡回路径。原始 f32 运算、取整、摆放、技能概率、候选支配关系和三队搜索算法均未修改。

## 测量方法

比较对象均为当前原生 f32 引擎，**不是旧整数版与新浮点版对比**。修改前、仅优化队友上界、全部三项优化分别保存独立 Release 二进制，均未启用实验缓存计数器。固定同一逻辑核心（亲和性掩码 4）和进程优先级，计时串行执行，不与构建、测试并行。

完整输入沿用：

- 新档案 1456 卡，活动 323，186 SP / 395 SP / 772 EX。
- 旧档案 1414 卡，原诊断的自定义活动，306 EX × 3。

最高分使用严格精准搜索；最大平均 PT 使用现有加权概率模型。每次记录输入和二进制 SHA-256、进程墙钟与 CPU 时间、阶段耗时以及完整结果。

## 分步试验

先仅修改队友上界，每场景每版一轮：

| 场景 | 修改前 | 仅队友上界复用 |
| --- | ---: | ---: |
| 1456 / 平均 PT | 57.186 s | 52.336 s |
| 1456 / 最高分 | 62.867 s | 70.131 s |
| 1414 / 平均 PT | 46.331 s | 35.574 s |
| 1414 / 最高分 | 32.102 s | 32.104 s |

这些总时间存在明显波动，不能据此声称单项优化在全部场景均有固定比例收益。1456 平均 PT 的上界初始化加查询累计从 1.574 秒降到 0.345 秒；整个剪枝准备仍从 11.867 到 10.836 秒，候选评分、贡献比较和三队搜索占据其他时间。

四组输出逐字段一致，全部非计时 metrics 一致。第一步之后再加入贡献上下文共享和延后存在性预计算，并单独重跑完整对照。

## 最终对照

下表是三项优化全部启用后的原生 Release 对照。1414 平均 PT 因首轮出现回退，交换执行顺序补测一轮并取两轮均值；其余三组各一轮。这里比较本轮修改前后的同一浮点引擎。

| 场景 | 修改前总耗时 | 修改后总耗时 | 耗时减少 | 候选构建：前 → 后 | 剪枝准备：前 → 后 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1456 / 平均 PT | 49.242 s | 41.393 s | 15.94% | 33.376 → 25.014 s | 10.659 → 3.432 s |
| 1456 / 最高分 | 52.744 s | 39.977 s | 24.21% | 31.887 → 23.301 s | 11.299 → 3.547 s |
| 1414 / 平均 PT，两轮均值 | 34.657 s | 32.209 s | 7.06% | 23.597 → 19.935 s | 6.942 → 2.466 s |
| 1414 / 最高分 | 28.666 s | 24.526 s | 14.44% | 18.600 → 14.573 s | 6.389 → 2.064 s |

“剪枝准备”取各道具组合 `prune_ms` 的总和，是候选构建的子阶段，不能再和候选构建相加。此阶段减少约 64%–69%；最终保留的候选数量不变，收益来自少做重复工作。

1414 平均 PT 的原始两轮如下，保留首轮回退记录：

| 轮次 | 执行顺序 | 总耗时：前 → 后 | 剪枝准备：前 → 后 | 三队求解：前 → 后 |
| --- | --- | ---: | ---: | ---: |
| 1 | 后、前 | 34.118 → 34.928 s | 6.596 → 2.682 s | 5.420 → 7.184 s |
| 2 | 前、后 | 35.196 → 29.490 s | 7.289 → 2.250 s | 5.092 → 5.424 s |

首轮剪枝准备已经减少 3.914 秒，但候选枚举评分与三队求解耗时增加，抵消了这部分收益。新档案最高分的三队求解也从 12.196 秒变为 9.462 秒，而这轮没有改变求解器或其工作计数。因此不能把所有总耗时差异都归因于这三项优化，也不承诺每次运行有相同加速比例。固定核心只能减少调度差异，不能消除频率、缓存及系统负载波动。

所有五对前后运行的完整业务输出逐字段相同，所有非计时 metrics 也相同。代表性的搜索工作量如下：

| 场景 | 原始候选字段 | 求解候选字段 | 三队工作计数 |
| --- | ---: | ---: | --- |
| 1456 / 平均 PT | `rawCandidateCount` 6,519,110 | `retainedCandidateCount` 78,186 | 第二队检查 1,196,068,789；第三队检查 19,760,261,009 |
| 1456 / 最高分 | `candidateCount` 5,865,840 | `solverCandidateCount` 26,149 | `exactWork` 6,211,291,216 |
| 1414 / 平均 PT | `rawCandidateCount` 3,974,578 | `retainedCandidateCount` 122,340 | 第二队检查 578,250,973；第三队检查 4,858,343,447 |
| 1414 / 最高分 | `candidateCount` 3,798,739 | `solverCandidateCount` 38,202 | `exactWork` 1,505,799,967 |

保留字段名称以区分两个入口原有的统计口径。最高分最终总分分别为 10,781,591 和 11,815,694；平均 PT 的分数和概率分布、卡牌、道具及推荐顺序也全部一致。

优化后，新档案平均 PT 的候选构建仍占 25.014 秒，其中 `build_candidate_ms` 累计 15.869 秒；三队求解为 9.596 秒。后续可继续调查候选评分与生成，而不再把主要成本归到队友上界缓存。

## 优化后的详细耗时

沿用上述最终运行日志，未额外重跑。下表单位为秒；旧档案平均 PT 使用两轮均值，其余各一轮。各项均累计所有道具组合。

| 阶段 | 新档案 / 平均 PT | 新档案 / 最高分 | 旧档案 / 平均 PT | 旧档案 / 最高分 |
| --- | ---: | ---: | ---: | ---: |
| 道具组合上界 | 1.935 | 2.247 | 1.819 | 1.756 |
| 候选构建合计 | 25.014 | 23.301 | 19.935 | 14.573 |
| 三队求解阶段 | 9.596 | 9.462 | 6.304 | 4.485 |
| 已记录的种子阶段 | 0.185 | 4.380 | 0.318 | 3.168 |
| 未单独计时部分及进程开销 | 4.663 | 0.587 | 3.833 | 0.544 |
| **进程总耗时** | **41.393** | **39.977** | **32.209** | **24.526** |

两种目标的 `seedMs` 口径不同：最高分统计初始种子搜索；平均 PT 只统计取得平均分候选后的 `approximate_mean_seed`，最早的 `seed_medley_raw_team_indices_for_items` 没有单独计时，落在最后一项。最后一项还包含未计时的整理、初始结果评分、输入输出及启动，因此不能把它全当作纯粹的杂项，也不能精确断言其中多少秒属于初始种子。

进一步拆开“候选构建合计”，下表是上一表该行的内部组成，不能重复相加：

| 候选构建内部 | 新档案 / 平均 PT | 新档案 / 最高分 | 旧档案 / 平均 PT | 旧档案 / 最高分 |
| --- | ---: | ---: | ---: | ---: |
| 剪枝准备 | 3.432 | 3.547 | 2.466 | 2.064 |
| 逐队候选评分与构建 | 15.869 | 16.100 | 11.575 | 10.123 |
| 枚举中的其余工作 | 2.751 | 3.063 | 2.081 | 2.042 |
| 平均分候选转换 | 1.571 | — | 2.944 | — |
| 筛选、整理及未分摊部分 | 1.391 | 0.590 | 0.870 | 0.344 |

其中“枚举中的其余工作”为 `enumerate_ms - build_candidate_ms`，包括组合遍历、分支上界、候选筛选以及最高分路径可能执行的当前最优值刷新；不是纯循环计时。“平均分候选转换”来自 PT 阶段日志的 `mean_ms`。最后一项由候选构建总时间扣除已列明阶段得到。

新档案两种目标的剪枝准备约 3.5 秒，内部已经不是队友上界查询主导：

| 剪枝准备内部 | 平均 PT | 最高分 |
| --- | ---: | ---: |
| 卡牌技能与综合力 profile | 0.249 | 0.262 |
| 上界初始化 | 0.244 | 0.271 |
| 同结构卡牌的贡献比较 | 1.003 | 1.033 |
| 固定点迭代剪枝 | 1.835 | 1.878 |
| 其他上下文和筛选开销 | 0.101 | 0.104 |

固定点迭代内部还包括贡献上下文、支配关系图、覆盖检查和上界查询，不能把这些内层计时再加到该表。上界查询本身仅为 0.025 / 0.026 秒。现有候选评分内部更细的 `candidate_profile_*` 是每 1024 次抽样记录，不作为全量阶段秒数，也不直接乘倍数来估算总成本。

## 正确性与接入

- 核心 248、数据层 28、三队求解器 23、WASM 接口 10，共 309 项 Release 测试通过；保留 11 项原有忽略项。
- 新增队友上界与完整扫描的逐位对照；已有小卡池穷举、单次及连锁延后贡献剪枝回归通过。
- 两份完整档案的 306 EX / 186 HD 单曲最高分与最大平均 PT，以及协力 PT，共 10 份输出与改动前保存的输出一致。
- 重建实际 WASM，10 组原生/WASM 对照通过，覆盖单曲、巡回、协力、Auto、技能延后及控分接口。
- 网页运行时资源标识为 `native-f32-5`，计分算术标识不变。未修改发行版本、提交或推送。

这里只记录原生性能对照；WASM 检查用于核对跨端结果，不据此给出浏览器加速比例。单曲完整档案检查与编译/其他测试存在并行，不作为单曲性能基准。
