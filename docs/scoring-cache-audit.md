# 浮点评分迁移后的缓存审计

日期：2026-09-21。覆盖组队和控分；不把三队、单曲、协力的缓存混为一谈。

后续组队优化见 [剪枝上下文复用](scoring-prune-context.md)，保留评分缓存，减少命中后仍发生的重复扫描和数组复制。

后续更正：下文最初的 5v5 153 秒案例存在 PT 反推漏掉活动加成的错误，不能作为正常性能或缓存保留的依据。修复后同一输入两次为 1.468 / 1.430 秒，见“5v5 慢查询根因与修复”。其他场景的缓存对照不受这处修复影响。

## 测量方法

增加非默认特性 `experimental-cache-audit`，逐次记录实际查询的命中、未命中及单个缓存的最大条目数。生产构建不启用计数器或环境变量开关；额外的 HashMap 探测也只在实验特性中编译。

基础测试包含新旧两份完整档案（1456 / 1414 张卡）的 18 个场景：

- 单曲最高分和最大平均 PT：306 EX、186 HD（技能延后）。
- 巡回三曲最高分和最大平均 PT：新档案活动 323 的 186 SP、395 SP、772 EX；旧档案 306 EX × 3。
- 协力平均 PT：沿用已经验证的协力场景，换入两份完整档案。
- 活动 320 对邦控分：Auto 50% / 75%，从 0 补齐 10,000 PT，只返回一份方案。

原生 Release，固定同一逻辑核（亲和性掩码 4），高于普通优先级，所有计时串行执行。命中统计按一个完整计算聚合，峰值条目数是单个缓存的最高水位；不是跨所有道具组合的累计驻留内存。

## 组队：应当保留

| 缓存 / 复用 | 键的含义 | 旧档案命中率 | 新档案命中率 |
| --- | --- | ---: | ---: |
| 单曲完整分数，306 EX | 浮点综合力位模式 + 六次技能类型 | 71.32% | 67.99% |
| 单曲完整分数，186 HD | 同上 | 44.16% | 52.92% |
| 单曲队伍综合力及摆放分组 | 排序后的五张卡 ID | 98.25%–98.39% | 97.54%–98.40% |
| 延后评分的综合力基础分 | 浮点综合力位模式 | 95.91% | 96.87% |
| 延后窗口分数增量 | 上述综合力内的技能及状态窗口 | 87.66% | 89.64% |
| 协力分数分布 | 五人浮点综合力、技能及追加触发者 | 65.05% | 70.76% |
| 巡回技能顺序种子 | 按位置排列的技能倍率类别 | 85.81%–85.82% | 78.35%–79.23% |
| 巡回平均 PT 的候选分布 | 候选 ID + 曲目位置 | 61.11% | 49.21% |

只有其中一部分直接以浮点综合力为键。队伍 ID、技能类型、状态窗口、候选 ID 没有因为迁移 f32 而失去重复性。相同卡组在不同技能顺序下，也会反复得到完全相同的浮点位模式。

实际缓存规模也没有失控：单曲完整分数缓存最高约 1564 项，单曲队伍综合力缓存最高约 118 项，延后综合力缓存最高约 78 项（上限 128）。协力分布缓存最高约 483 项，巡回候选分布最高约 64 项。种子缓存沿用每池 32768 槽的固定上限。统计在查询时采样，末次未命中后的插入可能使实际条目数再增加一项。

此外，95.00%–98.59% 的组队 `groups_for_charts` 调用，仍能证明全部物理摆放的第一段整数键分相同并直接共用一组。这是严格证明的评分等价，不是把相近浮点数舍入后当作相等；保留该优化和失败时的完整摆放分组。

## 控分：区分逐曲缓存与批量缓存

控分正式入口没有使用通用的 `CachedScore`（浮点综合力 → 分数），而是在固定技能上下文中按整数目标分数保存边界。`scoring/search.rs` 的通用浮点评分缓存目前仅被测试调用，删除它不能让正式引擎变快。

对邦四个场景，逐曲 `(谱面索引, 目标分数)` 缓存命中率为 0%–0.72%。Auto 50% 仅复用 5334 或 16002 个边界，却在批量准备中进行了约 188 万或 221 万次树查询；75% 两组没有命中。

批量缓存以目标分数为键，一次保存全部谱面的边界。把真正的整批复用与逐曲尝试探测分开计数后，整批命中率为 34.40%–49.07%；逐曲探测已有整批在这四组没有命中。每次整批命中避免数千次浮点边界反求，收益不能只看百分比。

| 场景 | 逐曲缓存：开启 → 关闭 | 批量缓存：开启 → 关闭 |
| --- | ---: | ---: |
| 新档案 50% | 2.940 → 2.848 s | 2.932 → 4.350 s |
| 新档案 75% | 3.341 → 3.342 s | 3.355 → 4.620 s |
| 旧档案 50% | 2.648 → 2.589 s | 2.637 → 3.512 s |
| 旧档案 75% | 2.499 → 2.491 s | 2.469 → 3.119 s |

逐曲缓存的关闭对照在 50% 下减少约 2.2%–3.1% 耗时，75% 基本持平。批量缓存关闭导致 26.3%–48.4% 的回退，必须保留。批量关闭实验仍生成当前查询所需的向量，只禁止重用已有答案，测的是重复计算代价，并非一个释放所有缓存内存的实现。

### 其他活动反例与查询结构试验

为避免只根据对邦删除缓存，另外用新档案实测国服 319 EX、318 协力、317 挑战、310 5v5 活动的 Auto 50% 控分。目标仍为补齐 10,000 PT，分别关闭逐曲缓存复测一次；所有开/关输出完全一致。

| 活动类型 | 逐曲缓存开启 | 关闭 | 说明 |
| --- | ---: | ---: | --- |
| EX | 1.270 s | 1.197 s | 此例没有逐曲命中 |
| 协力 | 1.380 s | 1.221 s | 此例没有逐曲命中 |
| 挑战 | 2.214 s | 2.361 s | 此例没有逐曲命中，单次耗时波动 |
| 5v5（修复前异常路径） | 153.268 s | 171.522 s | 受 PT 反推错误影响，不作为正常性能依据 |

修复前 5v5 的逐曲逻辑查询命中率只有 4.82%，但复用了约 298 万次浮点边界反求；批量命中率达到 99.17%，逐曲探测已有批量的命中率达到 85.69%。这些统计来自错误反推导致的多余搜索，撤回以此证明正常 5v5 需要逐曲缓存的结论。暂不改动共享缓存，缓存取舍仍需依据修复后的有效工作负载。

另外试验了把索引从 `(谱面索引, 目标分数)` 改为 `(目标分数, 谱面索引)`，按目标范围读取已有答案，再与完整谱面列表合并。这能减少树查询次数，但不能直接推导实际速度。

不启用审计计数器的正式 Release 二进制对照，每组前后交替两轮：

| 对邦场景 | 原结构 | 目标优先结构 | 耗时变化 |
| --- | ---: | ---: | ---: |
| 新档案 50% | 3.306 s | 3.147 s | −4.81% |
| 新档案 75% | 3.738 s | 3.894 s | +4.15% |
| 旧档案 50% | 2.927 s | 2.969 s | +1.43% |
| 旧档案 75% | 2.835 s | 2.833 s | −0.07% |

没有跨场景的稳定收益，故撤回该结构试验，保留原索引。八个控分场景的试验输出全部一致，但语义等价不等于更快。5v5 在本轮单次试验运行中为 182.293 秒；缺少同轮原结构的配对，因此不将它和此前的审计构建直接比较为回退幅度。

最终保留原有缓存及查询策略，只增加非默认的审计计数、开关对照能力和稀疏边界复用回归测试。没有保留缓存删除、浮点近似合并或未经证实的优化。

组队各缓存和摆放等价证明均保留。不存在从整数切换到浮点后，应当一概删掉这些复用机制的证据。

### 5v5 慢查询根因与修复

这里测的是国服活动 310 的 **Auto 50% 控分**，不是 5v5 多人竞演的最高分组队。输入为新档案 1456 张卡，从 0 补齐 10,000 PT、最多返回一份方案，数据及谱面列表保持不变。

`event_pt::solo_points(Festival)` 正算 PT 已应用活动加成；`score_range::pt` 却仍用不带加成的 `simple_interval` 反推分数。最终恢复队伍时再次正算，导致符合错误区间的带加成队伍被排除、正确的带加成解被漏掉。

例：14 万分、加成 50%、无火倍率，正算为 `floor((80 + floor(140000 / 14000)) × 1.5) = 135 PT`。正确的分数区间是 140000–153999，旧反推却给出 770000–783999。已将 Festival 反推改为 `bonus_interval`，保持两次取整和火倍率的顺序。

| 同条件原生 Release + 缓存审计 | 修复前 | 修复后 |
| --- | ---: | ---: |
| 进程总耗时 | 153.268 s（此前单次） | 1.468 / 1.430 s（两次） |
| 完成的目标搜索层 | 36 | 5 |
| 道具/队伍/目标区间检索累计 | 148.704 s | 0.038 s（第一次） |
| 最终方案 | 5 次、14 火、2 首曲目 | 2 次、5 火、1 首曲目 |
| 队伍活动 PT 加成 | 0% | 162% |

修复前的 35 个目标搜索层都没有返回候选，其中 3 次演出各层累计耗时约 86.47 秒。修复后在 2 次演出、5 火的层就找到解，无需继续扩大搜索；耗时下降约 99%，并非删除校验或收窄卡牌范围。

新方案为 33 EX，得分 1,027,437，每次基础 400 PT；分别使用 15 / 10 倍火倍率，得到 6000 + 4000 = 10000 PT。通过原始完整谱面和独立的指定队伍入口重算，摆放、显示综合力、活动加成以及全部可达技能顺序的得分和 PT 都一致。两次控分输出逐字段一致。

新增回归先在旧代码复现失败，再验证修复：覆盖 50%、37.5%、306% 加成的两侧分数边界、全部火倍率和跳过的不可达 PT；增加 Festival 带加成 MITM 与穷举五卡队伍的对照。全部 34 项控分相关测试通过。

本次复测为原生入口，尚未重建网页 WASM 或测浏览器耗时。评分缓存策略及浮点算术规则未修改。私有产物为 `festival-regression-before.log`、`festival-regression-after.log`、`festival-fixed-profile-festival.json`、`festival-fixed-repeat-profile-festival.json`、`1456-control-festival-bonus-fixed*.json/.log`、`festival-replay-validation.json`。

## 最终验证

- 全量 Release 回归：核心 245、数据层 28、三队求解器 23、WASM 接口 10，共 306 项通过，保留原有 11 项忽略项。
- 撤回查询结构试验后，重新运行全部 32 项控分相关回归，全部通过。新增用例覆盖稀疏/乱序谱面缓存、相邻目标分数及已知不可达答案。
- 重建默认原生和实际 WASM：10 组单曲/巡回最高分及平均 PT、指定队伍手动和 Auto、延后、协力及控分的跨端结果一致。
- 两份完整档案的四组控分，WASM 与既有原生输出完全一致；八个曲目方案使用原始完整谱面及指定队伍入口重算，摆放、显示综合力和每个可达技能顺序的得分均吻合。
- 网页与 Worker 资源标识更新为 `native-f32-4`，评分规则与结果缓存版本不变。JS 语法检查及 `git diff --check` 通过。

本轮没有把 Node 中的 WASM 验证时间当作正式基准：首次完整控分调用约 33 秒，后续约 3.7–4.6 秒，仍有明显首次调用成本。组队缓存命中统计与原生开关对照不能直接换算为浏览器端到端耗时。

## 复现

研究入口 `scripts/research/native-score-probe` 的 `cache-audit` 特性启用核心实验特性。`BANGDREAM_OPTIMIZE_DISABLE_CACHES` 支持以逗号分隔的缓存名称，用于同一二进制分别禁用 `single-score`、`single-power`、`queue-power`、`queue-delta`、`cooperative-score`、`medley-seed`、`medley-distribution`、`control-scalar`、`control-batch`。`power-plateau` 仅用于统计等价证明成功率。

本地私有产物位于忽略目录 `tmp/native-cache-audit/`：`manifest.json`、`profile.json` 保存 18 场景；`profile-auto.json` 保存拆分批量计数后的四组控分；`ablation.json` 保存 40 次开关对照；`other-controls*` 保存另外四类活动的开/关对照；`final.json` 保存 20 次结构试验验证，`mitm-target-first.rs` / `target-first.exe` 保留已撤回的试验。每次输出和日志均保留。核心四组巡回及四组控分输出与上一轮独立基准一致。原始玩家资料不进入版本管理。

`tests.log`、`final-tests.log`、`parity-final.json`、`control-wasm-final.json` 及 `wasm-final-validation.log` 保存最后的验证记录。
